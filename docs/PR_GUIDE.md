# PR 가이드

## 크기

**PR 1개 = 이슈 1개 = 작은 작업 1개.** 리뷰가 30분 안에 끝날 크기다.

| 좋은 PR | 나쁜 PR |
|---|---|
| 태양 스크롤 진입 연출 하나 | "메인 페이지 구현" |
| 자외선지수 API 중계 + 실패 시 안내 문구 | "백엔드 작업 여러 건" |
| 컬렉션 카드 목록 + 스모크 테스트 | "화면 + 리팩터링 + 문서" |

크기를 자를 수 없으면 아직 설계가 안 된 것이다 — 팀장에게 이슈를 쪼개 달라고 한다.

## 본문

양식([`../.github/pull_request_template.md`](../.github/pull_request_template.md))을 채운다. 반드시 들어가는 것:

- **첫 줄 `Closes #이슈번호`** — 머지 때 이슈가 닫히고 브랜치가 지워지는 연결 고리다
- 실행한 확인 명령과 **출력 그대로**
- 화면이 바뀌면 스크린샷, 움직임이 바뀌면 짧은 화면 녹화
- C형 이슈였다면 **질문 3개의 답** — 본인 말로 쓴다. AI 답을 복사하지 않는다

## 리뷰

### 리뷰어 (팀장)

- **동작을 확인한다.** "코드가 예쁘다"보다 "이게 되는가"
- 질문 답으로 **작업자가 코드를 이해했는지** 확인한다. 이해가 부족하면 머지 전에 한 번 더 설명을 요청한다
- 이슈의 "수정 허용 파일" 밖을 건드렸으면 되돌려 달라고 한다

### 리뷰받는 사람

- **"네 알겠습니다"로 무조건 수용하지 않는다.** 이해가 안 되면 코멘트로 되묻는다
- 반박해도 된다. 근거를 적으면 된다
- 리뷰는 학습 기회다. 지적이 아니다

## 머지

**팀장(봉준표)만 squash merge 한다.** 팀원은 Merge 버튼을 누르지 않는다 → [`GIT_RULES.md`](GIT_RULES.md)

## 영역이 겹칠 때

계약([`CONTRACT_API.md`](CONTRACT_API.md))이 바뀌는 PR은 **준표와 재원이 같은 PR에서 합의**한다. 머지 순서가 있으면 PR 설명에 적는다.

```
머지 순서: docs/contract-api-products → feat/back-products-api → feat/front-collection-data
계약이 먼저 안 들어가면 화면 쪽 mock과 서버 응답이 어긋난다
```

## 문서와 다르게 만들었을 때

코드로 우회하지 말고 **문서를 먼저 고친다.**

```
docs: errata — 광변색 색상 3색 → 5색
기획서 수정본 5. 광변색 소재에 빨강·주황·파랑·노랑·보라 5색으로 적혀 있다.
web-demo는 3색(바이올렛·코랄·스카이)으로 만들어졌다.
```
