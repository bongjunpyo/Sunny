# 이슈 가이드

**모든 작업은 이슈로 시작한다.** 구두·메신저로 정한 것은 없는 것으로 친다. 이슈는 팀장이 쓰고, **`back` 영역은 이재원이 직접 쓴다.** 권한 전체는 [`GIT_RULES.md`](GIT_RULES.md) "누가 무엇을 하나".

## 왜 이슈인가

- 팀원의 AI(Codex)는 대화가 끝나면 맥락을 잊는다. **이슈 본문이 다음 세션의 출발점**이다
- 브랜치 이름 · 수정 허용 파일 · 이름(함수·변수)이 이슈에 있으면 AI가 범위를 넘지 않는다
- 이슈와 PR 기록이 결과보고서의 "누가 언제 무엇을 했나" 근거가 된다

## 누가 쓰나

| 이슈 | 쓰는 사람 | 양식 |
|---|---|---|
| 조수희 작업 | **봉준표** | `작업 요청 (C형)` — 학습 섹션 포함 |
| 이재원 작업 (`back` 영역) | **이재원 직접** 또는 봉준표 — 확인 없이 시작 | `작업 요청 (C형)`. 학습 섹션(비유 · 질문)은 비워도 된다. **브랜치 · 수정 허용 파일 · 완료 기준은 반드시 적는다** |
| 버그 · 질문 · 요청 | 누구나 | 빈 이슈 — 담당자 배정은 팀장 |

이재원이 쓴 이슈라도 **계약(`CONTRACT_API.md`)이 바뀌면** 본문에 `@bongjunpyo`를 멘션하고 계약 PR을 먼저 연다 → [`GIT_RULES.md`](GIT_RULES.md) "교차 영역 작업".

## C형 이슈 — 섹션과 쓰는 법

GitHub에서 **New issue → 작업 요청 (C형)**을 고른다. 양식: [`../.github/ISSUE_TEMPLATE/task.md`](../.github/ISSUE_TEMPLATE/task.md)

| 섹션 | 쓰는 법 |
|---|---|
| 무엇을 만드나 | 기능을 2~3문장. 화면에서 무엇이 보이면 끝인지 |
| 브랜치 | `<종류>/<영역>-<설명>` 하나. **담당자는 이 이름을 그대로 쓴다** |
| 수정 허용 파일 | 표: 파일 · 새로/수정 · 역할. **표에 없는 파일은 만들거나 고치지 않는다** |
| 컴포넌트 · 함수 | 표: 이름 · 파라미터 · 타입 · 반환 · 하는 일. 가져다 쓰는 남의 함수는 "(가져다 씀)" 표시 |
| 변수 | 표: 이름 · 타입 · 위치 · 역할 |
| 완료 기준 | 체크박스. 테스트 출력 · 스크린샷(또는 화면 녹화) · 질문 답 |
| 먼저 읽을 것 | `web-demo/` 페이지나 문서 + 예상 시간 |
| 비유 | 핵심 부품 1~2개를 쉬운 비유로 |
| 끝나고 PR에 답 적기 | 이해를 확인하는 질문 3개 |
| 시작 — AI에 한 줄 | 담당자가 Codex에 그대로 붙여넣을 문장 |

**상세 단계가 긴 작업은 plan 파일을 따로 둔다** — `docs/superpowers/plans/YYYY-MM-DD-<브랜치 설명>.md`. 이슈의 이름 표는 plan에서 복사하고, **둘이 다르면 plan이 맞다**고 이슈에 적는다. 규칙은 [`superpowers/README.md`](superpowers/README.md).

## 담당자 · 라벨

- **Assignees에 담당자 한 명**을 지정한다. 담당자가 없는 이슈는 시작하지 않는다
- 라벨: `front` · `interaction` · `back` · `docs` · `bug`

## 이슈를 닫는 법

| 상황 | 닫는 법 | 브랜치 |
|---|---|---|
| 작업 완료 | PR 본문 `Closes #N` → **팀장이 머지하면 자동으로 닫힘** | 자동 삭제 (`delete_branch_on_merge`) |
| 취소 · 중복 | 팀장이 사유를 댓글로 남기고 닫음. **이재원은 자기가 쓴 `back` 이슈를 같은 방식으로 닫는다** | **닫는 사람이 원격 브랜치를 같이 삭제** |

그 밖에는 팀원이 이슈를 직접 닫지 않는다. 닫힌 뒤 로컬 정리는 [`GIT_RULES.md`](GIT_RULES.md) "이슈가 닫히면 브랜치도 닫는다".
