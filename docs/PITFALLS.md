# 실제로 난 실수들

여기 적힌 것은 **실제로 발생한** 실수다. 가정이나 일반론이 아니다. 사람을 탓하려는 기록이 아니라 **어느 장치가 비어 있었는지** 남기는 기록이다.

각 항목은 **증상 / 원인 / 어떻게 잡혔나 / 다음에**로 적는다. **"어떻게 잡혔나"가 제일 중요하다** — 어떤 확인이 실제로 효과가 있었는지 알려주기 때문이다.

기술 견본에서 난 실수(rAF 시계 혼용, SplitText 한글 줄바꿈 등)는 [`../web-demo/docs/PITFALLS.md`](../web-demo/docs/PITFALLS.md)에 있다.

## 1. 규칙이 main에 없었다

### 1.1 AI가 main에 직접 네 번 push했다 (2026-09-16)

- **증상** — 21:46~21:54 사이 main에 PR 없이 커밋 4개가 올라갔다(한국어 안내 문서 5개). 팀장의 작업 브랜치 `demo/web-tech-examples`에도 커밋 1개가 push됐다.
- **원인** — 장치가 전부 비어 있었다.
  - 팀 규칙(브랜치 → PR → 팀장 머지)은 설계 문서에만 있었고 **그 문서가 main에 없었다**
  - `.githooks/`가 없어 로컬에서 막는 장치가 없었다
  - **무료 요금제 비공개 저장소라 GitHub 브랜치 보호를 켤 수 없었다**
  - 팀원의 AI는 **Codex**라서, 규칙을 `CLAUDE.md`에 써 뒀어도 읽지 못했다 (Codex는 `AGENTS.md`를 읽는다)
- **어떻게 잡혔나** — 팀장이 `git log origin/main`에서 모르는 커밋을 봤고, `gh api repos/.../activity`로 **push 이벤트 4건과 브랜치 생성 1건**의 시각·대상을 확인했다. 활동 기록이 커밋 로그보다 정확했다 — 다른 브랜치에 들어간 push와 새 브랜치 생성까지 보였다.
- **정리** — 팀장이 main을 PR #1 머지 시점(`646500a`)으로 되돌렸다. 원격이 확인 시점과 달라졌으면 멈추도록 `--force-with-lease`를 썼다. 지운 커밋은 팀장 PC에 백업 브랜치로 남겼다.
- **다음에**
  - **규칙은 코드보다 먼저 main에 넣는다.** 온보딩 전에 `AGENTS.md`와 훅이 main에 있어야 한다
  - 규칙 원본은 **`AGENTS.md`** 하나. `CLAUDE.md`는 불러오기만 한다
  - 온보딩 1단계는 **훅 켜기**다
  - 팀원 PC에 남은 옛 커밋이 다시 push되지 않게, 되돌린 뒤 **팀원에게 로컬 정리 명령을 전달**한다

## 2. 전제를 확인하지 않고 설계를 얹을 뻔했다

### 2.1 대화에서 정한 역할·스택이 기획서 수정본과 달랐다 (2026-09-17)

- **증상** — 대화에서 "수희 = 페이지, 준표 = 3D, 백엔드 = Docker 별도 서비스"로 정해 규칙 파일을 쓰기 직전이었다.
- **원인** — 같은 날 올라온 `창업캡스톤디자인2_기획서(수정본)`의 5-1(스택)·5-2(역할)를 **원문으로 확인하지 않았다.** 수정본은 수희 = 인터랙션·3D, 백엔드 = Next.js 서버 API + Sanity + Supabase + Vercel이었다.
- **어떻게 잡혔나** — 규칙 파일을 쓰기 전에 수정본 hwpx를 텍스트로 뽑아 읽었다. 역할과 스택이 담당 폴더·금지 사항을 바꾸는 항목이라 쓰기 전에 팀장에게 확인했다.
- **다음에** — 담당·스택·예산처럼 **설계를 제약하는 사실은 제출 문서 원문에서 직접 확인**한다. 문서가 바뀐 날에는 다시 읽는다.
