# 시연 주문 요청 — #100

API/입력/DTO/오류/시연 정책의 정본 제안은 [CONTRACT_API.md 주문 절](../../docs/CONTRACT_API.md#주문-요청-저장본인-조회--시연-계약안)과 [계약 PR #101](https://github.com/bongjunpyo/Sunny/pull/101)이다. 공동 계약/운영 승인은 아직 남아 있다. 사용자 확인에 따라 동의 문구·버전은 시연 전용으로 준비했다. 환경변수 이름/위치는 [backend README](../README.md#주문-요청-시연--100--계약-101)가 원본이다.

## 구현 경계

- 여러 품목과 수량을 한 주문으로 저장한다. 팔찌는 네모 사진 칸 7개, 목걸이는 원형–달–원형 3개이며 목걸이에는 사진을 받지 않는다. 상세 제한/DTO는 계약을 따른다.
- PostgreSQL DB 세션 → 전체 품목/확인 의사/동의 검사 → 본인 verified 사진 잠금/대조 → 주문 묶음·품목·비즈·동의 영수증 원자 저장 → 본인 목록/상세 조회.
- 상태는 `REQUESTED`/`DEMO`다. 승인 안내는 시연용 주문 요청 저장 성공을 뜻한다. 실제/Toss 테스트 결제·SDK/키·결제 상태/금액·제작/배송 경로가 없다.
- owner별 멱등 키를 transaction advisory lock + UNIQUE로 직렬화한다. 정상화한 전체 품목 본문 해시가 다르면 충돌, 같으면 저장된 결과를 반환한다. 카탈로그/정책 재검사는 새 주문에 적용하며 커밋된 재요청은 스냅샷으로 응답한다.
- `0001`~`0004` SQL을 변경하지 않는다. 추가 `0005`에서 주문 묶음·품목 수량·비즈 모양/개수의 지연 제약을 적용한다. 기존 주문은 기존 7칸과 동의/시각을 보존하고 1품목 응답으로 조회한다. 새 목걸이만 3개 배치로 저장한다.
- 주문 관련 4개 테이블은 FORCE RLS, runtime SELECT/INSERT만 허용한다. 품목 수/수량 합계·연속 위치·같은 서버 시각·사진 제작 동의를 커밋 시 검사한다. timestamp는 millisecond 정밀도로 cursor 경계를 보존한다.
- 중복 사진 ID를 제거/정렬해 FOR SHARE로 잠그고 접근 차단 변경과 직렬화한다. 사진 바이트/키/서명 URL은 주문에 저장하지 않는다.

## 화면 연결

- #98 새 화면을 이재원 브랜치로 merge하고 기존 제품 그래픽을 재사용한다. 팀장 브랜치와 3D 씬 내부는 수정하지 않는다. 목걸이는 달 1개와 양옆 원형 2개로 표시한다.
- 상세/커스텀 → 여러 품목 장바구니 → 수량 조정 → 주문서 구성/사진 확인과 동의 → **결제하기** → 저장 성공 응답 확인 → `/orders` 이동으로 연결한다. 오류 때는 주문서와 장바구니를 유지한다.
- 장바구니는 세션 저장소에 옵션·수량·verified 사진 ID와 업로드 owner만 보존한다. 사진 바이트·서명 URL·인증 토큰은 보존하지 않는다. 동일 owner/본문의 멱등 키는 실패·새로고침 뒤에도 유지하며 성공 시 제출한 품목을 비운다.
- 회원/게스트 세션은 실제 인증 API로 확인한다. 세션 없이 페이지를 여는 것만으로 게스트 계정을 생성하지 않는다. 사용자가 ‘게스트로 계속’ 또는 ‘게스트로 사진 올리기’를 누르면 생성한다. 다른 세션의 사진은 주문에 연결하지 않는다.
- 커스텀 사진은 `photo-rules` 응답으로 허용 형식·용량·최소 해상도/입력 accept를 정하고 presign → 비공개 R2 PUT → complete 순서로 연결한다. PUT 실패 뒤에는 complete를 부르지 않으며 `UPLOAD_NOT_RECEIVED`를 검사 중/서비스 장애와 구분한다.
- 서버 검사 완료 사진만 배치한다. 장바구니/주문서에서 현재 세션의 read-url을 다시 발급하고 실제 이미지 로딩을 확인한다. 미리보기 실패나 사진/옵션/수량/세션 변경 시 확인을 다시 받는다. 제작 동의는 필수, 브랜드 동의는 선택이며 미선택을 true로 바꾸지 않는다.
- 현재 미리보기는 기존 SVG 구성 그림이다. 실물 치수/발색 시험·실제 3D 시청 완료를 입증하지 않는다. 확인 값은 사용자의 구성 확인 의사 기록이다.

## 안전한 검증

Node 24·Python 3·Docker·로컬 `postgres:17-bookworm` 이미지가 필요하다. 라이브러리 추가 없음.

```sh
cd frontend
npm ci
cd ..
python3 backend/orders/run-isolated-tests.py
```

- **backend/.env.local이 없는 별도 checkout에서만 실행**한다. 기존 파일이 있으면 덮어쓰지 않고 중단한다. `SUNNY_NODE_BIN`으로 Node 24 bin 경로를 지정할 수 있다.
- 무작위 이름/포트의 `sunny-order-test-*` PostgreSQL tmpfs 컨테이너만 만든다. 기존 sunny-dev/5434/볼륨·R2·사용자 키를 읽거나 변경하지 않는다. 계정·사진 메타데이터는 합성이다.
- versioned role 초기화/동일 migration runner로 0001~0004를 적용한 뒤 합성 기존 주문과 7칸을 만든다. 0005 적용 전후 원본 필드/비즈 보존과 전체 migration 재실행 skip을 확인한다.
- 주문/인증/사진 테스트 후 실제 Next HTTP에서 명시적 게스트 생성 → 혼합 품목 주문/멱등 → 본인 목록/상세 → 로그아웃을 확인한다. 외부 R2·Resend·카카오·Toss 요청은 하지 않는다.
- UI 점검은 `SUNNY_ORDER_UI_HOLD=1`을 선택한다. 비공개 ready 파일을 정할 때 `SUNNY_ORDER_UI_STATE`를 사용한다. 출력된 loopback 주소의 **실제 상품·장바구니·주문서**를 검사하고 ready JSON의 releaseFile을 생성하면 종료한다. 10분 뒤에는 실패로 종료한다. `--ui-only`는 이미 검증한 DB/API 테스트 묶음을 생략하고 migration/실제 HTTP/UI만 실행한다.
- 임시 설정/키는 0600, 임시 디렉터리는 0700이다. 종료 시 자신이 만든 라벨의 컨테이너만 제거하고 임시 설정을 정리한다. 기존 DB/볼륨에 대한 정리 명령은 없다.

2026-11-03 검증: 주문 17/17, 인증 23/23, 사진 21/21, 프론트 로직 49/49, 기존 화면 회귀 E2E 데스크톱/모바일 2/2, Python 19 pass/7 opt-in skip, typecheck/build 성공. 실제 Chrome에서 혼합 장바구니·수량/새로고침 유지·첫 저장 503 후 같은 키 재시도·성공 목록 이동/상세·390px 가로 넘침 없음을 확인했다. 실제 photo-rules의 작은 이미지 차단과 다른 합성 규칙 응답에 따른 안내/accept 변경도 확인했다. R2 실제 객체 업로드는 실행하지 않았으며 업로드 adapter 흐름은 응답 모의 테스트로 검증했다.

## 운영/기존 DB 적용 전

#92 인증 → #94 사진과 계약 #101의 팀장 리뷰/머지 순서를 확인한다. 화면 #98은 main에 반영됐다. 일회성 로컬 이관 #96은 완료 후 미병합 종료되어 이 PR의 선행 머지 대상에서 제외한다. 팀장 요청에 따라 이관 도구·전용 문서/테스트를 제거했으며, #102의 base 변경은 팀장이 진행한다. **현재 기존 sunny DB에는 0004·0005를 적용하지 않았다.** 기존 로컬 데이터·백업 정리는 #92·#94 머지와 안정화 뒤 별도로 판단한다.

실제 카탈로그/Sanity·주문 가능 상태·정책 문구/버전/시행일·개인정보 보관/철회·공유 남용 제한과 운영 전 검증이 남아 있다. 시연은 개발 loopback 전용이며 production/원격 Origin에서는 flag와 무관하게 차단한다. 실제 설정·배포값을 이번 작업에서 바꾸지 않는다.

설계 근거: [주문 API 정본](../../docs/CONTRACT_API.md#주문-요청-저장본인-조회--시연-계약안)과 구현 테스트를 함께 검토한다.
